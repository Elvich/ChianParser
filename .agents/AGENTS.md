# Правила написания кода для проекта ChianParser

Этот файл определяет правила и стандарты разработки для клиентской части (Swift/SwiftUI) и серверной части (Python/FastAPI) проекта ChianParser.

---

## 🏛️ 1. Чистая архитектура и внедрение зависимостей (DI)

- **Разделение слоев (MVVM)**:
  - **View (Представление)**: Отвечает исключительно за отображение интерфейса и обработку пользовательского ввода. Не содержит бизнес-логики, прямого обращения к базам данных (SwiftData) или сетевых запросов.
  - **ViewModel (Модель представления)**: Управляет состоянием интерфейса, форматирует данные для View, координирует вызовы сервисов. Связывается с View через `@Observable` (для Swift 5.9+).
  - **Model (Модель)**: Описывает структуры данных (`Apartment`, `PricePoint`). Допускаются только легковесные вычисляемые свойства, не требующие внешних зависимостей.
  - **Services (Сервисы)**: Инкапсулируют бизнес-логику (парсинг, анализ, экспорт). Общаются друг с другом и с ViewModels только через протоколы.
- **Внедрение зависимостей (Dependency Injection)**:
  - Все сервисы и менеджеры должны регистрироваться в DI-контейнере [AppContainer](file:///Users/elvi4/Projects/Swift/ChianParser/App/ChianParser/App/AppContainer.swift).
  - Создание экземпляров сервисов напрямую внутри View или ViewModels **запрещено**. Зависимости должны передаваться через инициализатор (Constructor Injection) или извлекаться из `AppContainer`, проброшенного через Environment.

## 🍎 2. Стандарты разработки на Swift (App)

- **Безопасность типов и опционалы**:
  - Категорически избегайте принудительного извлечения опционалов через `!`. Используйте `guard let`, `if let`, оператор объединения с nil (`??`) или `compactMap`.
- **Контроль доступа**:
  - Всегда явно указывайте модификаторы доступа: `private` для внутренних свойств и вспомогательных методов, `fileprivate` при необходимости, `internal` (по умолчанию) для модульных сущностей и `public` для открытых интерфейсов.
- **Асинхронность и многопоточность**:
  - Тяжелые операции (парсинг HTML/JSON, вычисление скоринга по большой выборке, сетевые запросы) должны выполняться в фоновом режиме с использованием Swift Concurrency (`Task`, `actor`, `ParserActor`).
  - Обновление UI должно происходить строго на главном потоке (`@MainActor`).
- **Именование (API Design Guidelines)**:
  - Используйте camelCase для переменных и методов, PascalCase для типов (классов, структур, перечислений, протоколов).
  - Имена методов должны читаться как грамматические фразы (например, `buildBenchmark(from:targetPercentile:)`, а не `benchmarkBuilding(apts:perc:)`).

## 🐍 3. Стандарты разработки на Python (Backend)

- **Асинхронность**:
  - Маршруты FastAPI (route handlers), выполняющие ввод-вывод или запросы к БД, должны быть объявлены как `async def`.
- **Типизация и валидация**:
  - Обязательно используйте аннотации типов для аргументов функций и возвращаемых значений.
  - Для валидации входящих и исходящих данных используйте схемы `pydantic`.
- **Структура**:
  - Маршруты должны быть разбиты на модули и подключаться к главному приложению через `APIRouter` (например, в директории `api/routes/`).

## 💬 4. Документирование и комментирование

- **Язык**:
  - Все комментарии в коде, сообщения об ошибках для логов и документация к методам (Docstrings / Swift Markdown Comments) должны быть написаны **исключительно на русском языке**.
- **Качество описания**:
  - Документируйте неочевидные алгоритмы (например, веса в `FlipAnalyzer` или логику обхода капчи в `CianWebView`).

## 🐙 5. Правила работы с Git

- **Формат коммитов (Conventional Commits)**:
  - Пишите коммиты на русском языке, используя стандартные префиксы:
    - `feat: ` — добавление новой функциональности.
    - `fix: ` — исправление багов.
    - `refactor: ` — рефакторинг кода без изменения логики.
    - `docs: ` — обновление документации.
    - `style: ` — правка форматирования, отступов.
- **Ветвление**:
  - Разработка новых фич должна вестись в отдельных ветках (например, `feature/dynamic-scoring`), которые сливаются в `main` через Pull Requests после проверки.
